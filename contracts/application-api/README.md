# `contracts/application-api` — client-facing API contract

**Status: proposed design, not implemented.**

The OpenAPI specification for `services/backend`, consumed by `apps/mobile` and
`apps/admin`.

| File | What it is |
|---|---|
| [`openapi.design.json`](openapi.design.json) | The **proposed** client-facing contract (37 operations), awaiting the Phase 00 contract freeze |
| [`examples/`](examples/) | Synthetic response fixtures — a four-level catalog, four sequential evaluation outcomes, and two error envelopes |

The fixtures are mock payloads for wiring clients against, **never** evidence of model
quality or a reviewed curriculum. `contracts/shared/integration-cases.json` sequences the
four evaluation outcomes into a personal-best comparison scenario.

Defined by [`docs/phase-0-baseline.md`](../../docs/phase-0-baseline.md) §5.3 and §10.

Per §5.3 the **OpenAPI document generated by FastAPI is authoritative**. `openapi.design.json`
is a design proposal that predates the backend: once the FastAPI skeleton exists, generate
its OpenAPI and check it against this document in CI rather than maintaining two drifting
sources of truth. Where this document conflicts with
[`docs/phase-0-baseline.md`](../../docs/phase-0-baseline.md), the baseline wins — see the
divergence note in [`docs/implementation/README.md`](../../docs/implementation/README.md).

Representative surface (§10): `/health/live`, `/health/ready`, `/api/v1/me`,
`/api/v1/children/...`, `/api/v1/curriculum/...`, `/api/v1/media/{media_id}`, and the
`/api/v1/admin/...` group.

All endpoints use consistent error envelopes, correlation IDs, validated schemas, and
server-side authorization checks.
